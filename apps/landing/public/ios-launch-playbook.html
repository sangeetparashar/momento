00

Prerequisites & Tools

One-time · ~2 hours

Before you start, you need accounts on three different platforms and a Mac with developer tooling installed. Skip this section if you've already done all of it on this machine.

00.1Apple Developer Account One-Time

You need a paid Apple Developer Account ($99/year) to submit any app to TestFlight or the App Store. Free accounts cannot distribute.

  1. Sign up at developer.apple.com
    Browser→ developer.apple.com/programs/enroll https://developer.apple.com/programs/enroll
    Pay $99 USD. Approval is usually instant for individuals, 1-3 days for organizations.
  2. Note your Team ID
    After approval, find your Team ID (10-character alphanumeric):
    developer.apple.com/account→ Membership Details
    Looks like ABCD123XYZ. You'll need this throughout the playbook.

00.2EAS / Expo Account One-Time

EAS (Expo Application Services) handles cloud builds, credentials, and App Store submission. Free tier gives ~30 builds/month; paid tiers start at $19/month.

  1. Sign up at expo.dev
    Browser→ expo.dev/signup https://expo.dev/signup
  2. Install EAS CLI locally
    npm install -g eas-cli
    Or use npx eas-cli@latest <command> on demand without global install.
  3. Authenticate
    eas login
    Verify with eas whoami — should print your Expo username.

00.3Local Tooling on Mac

export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8
Add to your ~/.zshrc or ~/.bash_profile to make permanent.

00.4Decide Your Bundle ID

The bundle identifier is your app's unique global ID. Format: reverse-DNS, lowercase, no hyphens preferred. Examples: com.acme.appname, com.yourcompany.product.

  • Must be globally unique — no two App Store apps can share one
  • Cannot change after first build — pick carefully
  • Convention: com.<domain>.<appname> or net.<domain>.<appname>

Throughout this playbook we'll use com.example.yourapp as the placeholder — substitute your real bundle ID.

01

Project Configuration

~30 min one-time

Configure app.json, eas.json, and any necessary Expo config plugins. This is the only "code change" work in this playbook.

01.1app.json — Expo configuration

Minimum required iOS fields in apps/mobile/app.json (or wherever your Expo app lives):

{
  "expo": {
    "name": "Your App Name",
    "slug": "your-app-slug",
    "version": "1.0.0",
    "owner": "your-eas-username",
    "ios": {
      "bundleIdentifier": "com.example.yourapp",
      "buildNumber": "1",
      "supportsTablet": false,
      "infoPlist": {
        "ITSAppUsesNonExemptEncryption": false
      }
    },
    "plugins": [
      "expo-router",
      "./plugins/with-ios-script-sandboxing"
    ]
  }
}
✓ Why ITSAppUsesNonExemptEncryption matters Setting this to false in your Info.plist makes Apple auto-pass the Export Compliance check — no manual "Missing Compliance" dialog needed when the build appears in TestFlight. Save yourself a step.

01.3Expo config plugin: iOS sandboxing fix If using Xcode 15+

Xcode 15+ defaults ENABLE_USER_SCRIPT_SANDBOXING=YES which breaks React Native builds with Sandbox: bash deny(1) file-write-create. Since apps/mobile/ios/ is gitignored in Expo managed workflow, any direct Podfile fix gets wiped on next expo prebuild. Solution: an Expo config plugin that injects the fix.

Create apps/mobile/plugins/with-ios-script-sandboxing.js:

const { withDangerousMod } = require('@expo/config-plugins');
const fs = require('fs');
const path = require('path');

module.exports = function withIosScriptSandboxing(config) {
  return withDangerousMod(config, [
    'ios',
    async (config) => {
      const podfilePath = path.join(config.modRequest.platformProjectRoot, 'Podfile');
      let contents = fs.readFileSync(podfilePath, 'utf-8');

      const snippet = `
    installer.pods_project.targets.each do |target|
      target.build_configurations.each do |config|
        config.build_settings['ENABLE_USER_SCRIPT_SANDBOXING'] = 'NO'
      end
    end
    installer.aggregate_targets.each do |target|
      target.user_project.native_targets.each do |native_target|
        native_target.build_configurations.each do |config|
          config.build_settings['ENABLE_USER_SCRIPT_SANDBOXING'] = 'NO'
        end
      end
      target.user_project.save
    end`;

      if (!contents.includes('ENABLE_USER_SCRIPT_SANDBOXING')) {
        contents = contents.replace(
          /post_install do \|installer\|/,
          `post_install do |installer|${snippet}`
        );
        fs.writeFileSync(podfilePath, contents, 'utf-8');
      }
      return config;
    },
  ]);
};

Then reference it in app.json's plugins array (see 01.1). This survives expo prebuild --clean and EAS cloud builds.

01.4Verify clean build locally

Before involving Apple/EAS, verify your local build works:

cd apps/mobile
npx expo prebuild --platform ios --clean
cd ios
export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8
pod install
cd ..
npx expo run:ios --device "iPhone 17"

If this succeeds and the app launches on the iOS simulator with your account/auth working, you're ready for EAS cloud builds.

02

Apple Developer Portal Setup

~15 min · One-time per app

Register your bundle identifier and generate the APNs (Apple Push Notification service) key. Other certificates and provisioning profiles are auto-managed by EAS — you don't touch them.

02.1Generate APNs Key Apple Portal Account-Wide

⌁ Scope One APNs key works across all apps in your Apple Developer account. You only need to do this once, ever, per team.
  1. Open Keys section
    developer.apple.com/account→ Certificates, Identifiers & Profiles→ Keys (left sidebar) https://developer.apple.com/account/resources/authkeys/list
  2. Create new key
    Click the (+) button next to "Keys" header.
    • Key Name: YourApp APNs Key
    • Check Apple Push Notifications service (APNs)
    • Click Continue → Register
  3. Download the .p8 file
    Apple shows you the Key ID (10-char alphanumeric, e.g. 7PA9M865VN) and a one-time download link.
    ⚠ One-Time Download Apple will NEVER show you this file again. Download immediately. Save to your password manager + a secure local location. If you lose it, you must revoke and regenerate (which invalidates all existing builds using it).
    Filename format: AuthKey_<KEY_ID>.p8 (e.g. AuthKey_7PA9M865VN.p8).
  4. Place it in your mobile app folder
    Copy to apps/mobile/AuthKey_<KEY_ID>.p8. Add to .gitignore. Never commit this file.
  5. Note the Key ID and Team ID
    You'll need these in Section 04. Write them down:
    • APNs Key ID: shown next to the key in Apple Portal (e.g. 7PA9M865VN)
    • Apple Team ID: from Membership Details (e.g. 9BJL3C9DHA)

02.2Bundle ID registration Apple Portal

You typically don't need to register the bundle ID manually. EAS will register it automatically on first build when it provisions credentials. But if you want to pre-register:

  1. Open Identifiers section
    developer.apple.com/account/resources→ Identifiers→ (+) button
  2. Register App ID
    Choose App IDs → App → fill in:
    • Description: human-readable name
    • Bundle ID: Explicit selected, enter com.example.yourapp
    • Capabilities: check Push Notifications (and any others your app uses: Sign in with Apple, Associated Domains, etc.)
    Continue → Register.
03

App Store Connect App Creation

~10 min · One-time per app

Create the App Store Connect "app" record. This is the entity that holds your TestFlight, builds, store listing, App Privacy declarations, etc.

  1. Open ASC home
    Browser→ appstoreconnect.apple.com→ Apps https://appstoreconnect.apple.com/apps
    Sign in with the Apple Developer account email.
  2. Create new app
    Click the blue (+) button → New App. Fill in:
    • Platforms: ✓ iOS (uncheck macOS, visionOS unless needed)
    • Name: how it appears in App Store search (max 30 chars; can change later but only before first submission)
    • Primary Language: e.g. English (U.S.)
    • Bundle ID: pick the one you registered in 02.2 from the dropdown
    • SKU: internal identifier, never shown to users. Use yourapp-ios-001 or similar
    • User Access: Full Access
    Click Create.
  3. Note the App ID
    After creation, the URL contains your ASC App ID (10-digit number): 
    https://appstoreconnect.apple.com/apps/1234567890/...
    Save this — it goes into eas.json's submit.production.ios.ascAppId field.
  4. Update eas.json with ASC App ID
    Edit the submit block from Section 01.2: 
    "submit": {
  "production": {
    "ios": {
      "appleId": "you@example.com",
      "ascAppId": "1234567890",
      "appleTeamId": "ABCD123XYZ"
    }
  }
}
    Commit and push this change.
04

APNs Key Upload to EAS

~3 min

EAS needs the APNs .p8 key (generated in Section 02) so its build pipeline can sign push notification payloads in production builds.

  1. Run the credentials wizard
    cd apps/mobile && npx eas-cli credentials --platform ios
  2. Navigate the interactive menu
    1. Build profile? → pick any (keys are account-level)
    2. What do you want to do? → Push Notifications: Manage your Apple Push Notifications Key
    3. Set up a Push Notifications Key for your project
    4. Upload your own key (NOT "Use existing from Apple Portal" — that requires Apple credentials and refetches; you have the file locally)
    5. Fill in:
      • Path: ./AuthKey_<KEY_ID>.p8
      • Key ID: from Apple Portal (e.g. 7PA9M865VN)
      • Team ID: usually auto-filled from eas.json
    6. Quit menu
  3. Verify it stuck
    Re-run npx eas-cli credentials --platform ios and pick "Set up your project to use Push Notifications". You should see "Push Key is already set up for <your-app> com.example.yourapp" with the Key ID confirmed.
⌁ Once and done The same APNs key works for every iOS app in your Apple Developer team. You only repeat this section if you regenerate the key or switch developer accounts.
05

EAS Production Build

~25-35 min queue + build

EAS spins up a macOS cloud worker, runs expo prebuild, installs CocoaPods, generates Apple distribution certificates and provisioning profile (first build only), then runs fastlane to produce a signed .ipa uploaded to EAS storage.

  1. Ensure working tree is clean
    git status
    EAS uploads your project files; uncommitted changes go into the cloud build. Commit anything important first.
  2. Trigger the production build
    cd apps/mobile && eas build --profile production --platform ios
  3. Confirm bundle identifier
    EAS reads com.example.yourapp from your app.json (or the existing ios/ folder if you've prebuilt locally). Press Enter to confirm.
  4. Apple credentials provisioning (first-time only)
    EAS asks:
    • "Do you want to log in to your Apple account?" → yes
    • Apple ID: enter the Apple Developer account email
    • 2FA code: enter the 6-digit code Apple pushes to your trusted device
    • Generate a new Apple Distribution Certificate? → yes
    • Generate a new Apple Provisioning Profile? → yes
    EAS stores the cert + profile in its credentials service. On subsequent builds, it reuses them automatically (no prompts).
  5. Build queues and runs
    EAS prints a build URL like: 
    https://expo.dev/accounts/<username>/projects/<app>/builds/<uuid>
    Free tier queue: 5-15 min wait before the build starts. Build itself runs ~20-25 min. Total wall-clock 25-45 min.

    You can close the terminal. The build continues in the cloud. Click "Notify me" on the build page to get an email when done.
  6. Watch for green checkmarks
    The build page shows steps:
    • Prepare project ✓
    • Install dependencies ✓ (~12s)
    • Prepare credentials ✓
    • Install pods ✓ (~10s)
    • Bundle JavaScript ✓ (~13s)
    • Run fastlane ✓ (~3-5 min) — actual Xcode archive + signing
    • Upload application archive ✓
    If any step fails, click it to see logs. Most failures are dependency conflicts or signing issues.
⚠ Yellow warnings are usually OK Build logs often show 3,000+ third-party pod warnings (Reanimated, SDWebImage, RNSVG nullability noise). Ignore them. Only red error: lines block. To filter: 
gunzip -c <log>.xcactivitylog | strings | grep -E 'error:' | head -20
06

EAS Submit to App Store Connect

~5 min CLI + ~10 min Apple processing

EAS Submit uploads the IPA from EAS storage to App Store Connect using Apple's Transporter service. On first run it auto-generates an App Store Connect API Key for future submits (no more 2FA dance).

  1. Run submit on the latest build
    cd apps/mobile && eas submit --platform ios --latest
  2. ASC API Key generation (first-time only)
    EAS asks: "Generate a new App Store Connect API Key?" → yes.

    EAS uses your cached Apple session to mint an API key scoped to this app. The key is stored on EAS servers; you don't manage it manually. Output: 
    Created App Store Connect API Key.
App Store Connect API Key assigned to com.example.yourapp for EAS Submit.
Using Api Key ID: ABC123XYZ ([Expo] EAS Submit ...)
  3. Upload runs
    EAS prints a submission URL and runs the upload (~2-5 min). When CLI completes, you'll see: 
    ✓ Submitted your app to Apple App Store Connect!
Your binary has been successfully uploaded to App Store Connect!
  4. Wait for Apple processing (5-15 min)
    The CLI is done but Apple processes the binary server-side. You can close the terminal. Apple emails you when processing finishes. To check manually:
    App Store Connect→ Your App→ TestFlight tab→ iOS (left sidebar Builds)
    When the build appears with status "Ready to Submit" (yellow dot), Apple's processing is complete.
✓ ASC API Key is reusable forever Every future eas submit uses this same auto-generated API key. No 2FA, no app-specific passwords. The key is bundle-scoped so it can only submit this specific app.
07

Privacy Policy Hosting

~30 min

Apple requires a public Privacy Policy URL for any external testing or App Store distribution. If the URL doesn't load when Apple's reviewer clicks it, your submission is rejected. Set this up before submitting for Beta App Review.

07.1Required content

Apple has no strict template, but the policy must cover:

  • What data you collect — be specific (email, name, location, content, device tokens, etc.)
  • How you use it — auth, content delivery, push, fraud prevention, etc.
  • Third parties you share with — every SDK and service (Privy, Firebase, Stripe, etc.)
  • User rights — access, correction, deletion (GDPR/CCPA-aligned language)
  • Account deletion — Apple specifically requires in-app account deletion as of 2022
  • Children's privacy — COPPA / GDPR-K compliance
  • Contact info — a real email address
  • Effective date

07.2Hosting

Simplest path: drop an HTML file in your existing landing site's public directory and deploy.

  1. Create the file
    Path: apps/landing/public/privacy.html (or wherever your static-served public dir is). Use a clean dark theme matching your brand. Reference the Momento privacy page at /privacy.html as a model.
  2. Commit and push
    git add apps/landing/public/privacy.html
git commit -m "docs: add privacy policy"
git push origin main
  3. Verify URL is live
    Vercel auto-deploys (~60-90 sec). Test: 
    curl -I https://your-domain.com/privacy.html
    Should return 200 OK. If 404, check Vercel deployment status.
  4. Save the URL — you'll paste it in Section 09 and 10
    Format: https://your-domain.com/privacy.html
⚠ Domain must resolve If you're using a custom domain (e.g. yourapp.com) but the domain DNS isn't pointed at your hosting yet, Apple's reviewer will see a parked page or 404 and reject. Either (a) point DNS first, or (b) use the auto-generated Vercel URL (landing-xyz.vercel.app/privacy.html) until DNS is wired.
08

ASC App Privacy Questionnaire

~15-20 min

Apple's App Privacy declaration. Mandatory before any distribution. Declares every data type your app collects, whether it's linked to user identity, and whether it's used to track. This populates the "Data Linked to You" / "Data Not Linked to You" labels shown on your App Store listing.

08.1Navigate to App Privacy

App Store Connect→ Your App→ Distribution tab→ left sidebar App Store section→ App Privacy

08.2Enter the Privacy Policy URL

Click Edit next to Privacy Policy → paste the URL from Section 07 (https://your-domain.com/privacy.html) → Save.

08.3Declare data types

Click Get Started (or Edit next to Data Types). Apple shows ~14 categories of data:

CategoryExamples
Contact InfoName, Email, Phone, Address
Health & FitnessHealth, Fitness data from HealthKit
Financial InfoPayment info, Credit Score, Other Financial
LocationPrecise Location, Coarse Location
Sensitive InfoRace, Sexual Orientation, Religious Beliefs
ContactsContact lists from device address book
User ContentPhotos/Videos, Audio, Gameplay, Customer Support, Other User Content
Browsing HistoryWeb browsing in-app
Search HistoryIn-app search
IdentifiersUser ID, Device ID
PurchasesPurchase History

For each type you collect, check the box. Then for each, Apple asks:

  1. What is this data used for? (multi-select: App Functionality, Analytics, Product Personalization, Developer's Advertising, Third-Party Advertising, Other)
  2. Is this data linked to the user's identity? (Yes/No)
  3. Is this data used to track the user? (Yes/No)

08.5Publish

After all checked data types are filled in (no more yellow ⚠ triangles), the blue Publish button at the top-right of App Privacy activates. Click it → confirm. Status flips to "Published" and the declaration locks in.

⚠ Mandatory before Beta App Review Apple silently hides the "Submit for Review" button on your external testing group until App Privacy is Published. If you can't find the submit button later (Section 13), come back here first.
09

ASC App Information

~10 min

Categories, age rating, content rights, license agreement. Required for any distribution.

09.1Navigate to App Information

App Store Connect→ Your App→ Distribution tab→ left sidebar General section→ App Information

09.2Categories

  • Primary Category (required): the most accurate category for App Store browsing. Pick one.
  • Secondary Category (optional): another category your app fits. Doesn't appear in App Store search but adds taxonomy.

Common categories: Social Networking, Lifestyle, Photo & Video, Productivity, Business, Finance, Entertainment, Utilities, News, Health & Fitness, Education.

09.3Content Rights

Click Edit → answer "Does your app contain, show, or access third-party content?":

  • "Yes, this app has the necessary rights to its third-party content" — pick this if users post user-generated content and your Terms of Service grants you license to host it.
  • If the app uses no third-party content at all → "No"

09.4Age Rating questionnaire

Click Edit next to Age Rating. Apple asks ~12 questions covering violence, sexual content, profanity, alcohol/drugs, gambling, etc.

Two critical questions for most social/UGC apps:

  • User-Generated Content: ✓ Yes if users post (text, image, video, comments)
  • Unrestricted Web Access: ✓ Yes if your app shows arbitrary URLs (creator links, embedded media)

Result is typically 17+ or 18+ for UGC-heavy apps. This is normal and unavoidable.

09.5License Agreement

Click Edit → choose:

  • Apple's Standard License Agreement — recommended default. Covers most apps.
  • Custom EULA — only if you have specific licensing needs (rare for B2C apps).

09.6Save

Click Save top-right. The yellow warning indicators next to each section disappear.

11

Internal Testing Group

~10 min

Internal testers get instant access to builds — no Apple review required. Limited to 100 testers, all of whom must be Users in your App Store Connect team.

11.1Add testers to ASC Users and Access

Each internal tester must first be added as an ASC user. Do this for every tester.

  1. Open Users and Access
    App Store Connect→ top nav: Users and Access→ People tab
  2. Add new person
    Click (+) Add People. Fill in:
    • First Name + Last Name
    • Email: the tester's Apple ID email — must be the one they use to sign into iCloud on their iPhone
    • Roles: Developer, Marketing, App Manager, or Admin — all grant TestFlight access. Pick based on what other permissions they need.
    • Apps: check the specific apps they should access (or "All Apps")
    Click Invite.
  3. Tester accepts the invitation
    Apple emails the tester. They click the invitation link → sign in with their Apple ID → accept. They become an ASC team member.

11.2Create Internal Testing group

  1. Navigate to Internal Testing
    ASC→ Your App→ TestFlight tab→ left sidebar (+) next to INTERNAL TESTING
  2. Configure group
    • Group Name: e.g. Your App Core Team
    • Enable automatic distribution: ☑ ON (new builds auto-attach to this group)
    Click Create.
  3. Add testers to the group
    Inside the group page → Testers tab → (+) → modal shows all ASC users from step 11.1 → check the ones to add → Add.
  4. Attach a build
    Inside the group page → Builds tab → (+) → select the latest processed build → Add. Optionally fill in "What to Test" for this group → confirm.
✓ Internal tester invites work instantly No Apple review. Testers receive an email + push notification in the TestFlight app immediately after adding them + attaching a build. They install via the TestFlight app on their iPhone.
12

External Testing + Public Link

~10 min setup + ~24h Apple review

External testers can be invited by email (no ASC team membership) or via a public link (anyone can self-onboard). Up to 10,000 testers. First build needs Beta App Review by Apple (~24h).

  1. Create the External Group
    TestFlight tab→ left sidebar (+) next to EXTERNAL TESTING
    • Group Name: e.g. Your App Public Beta
    • Click Create
  2. Attach the build
    Group page → Builds tab → (+) → select the same build you attached to Internal Testing → Add. A "What to Test" modal appears — paste: 
    Initial public beta. Test: [list key features]. Shake to send feedback. Crashes auto-report.
  3. Enable Public Link
    Group page → Settings tab → scroll to Public Link section:
    • Toggle Enable Public Link ☑
    • Tester Limit: set to 500 initially (max 10,000)
    Save. Apple generates a URL like: 
    https://testflight.apple.com/join/aBcD1234
    Copy it. It won't work until Apple approves the build (next step).
13

Submit for Beta App Review

~5 min + ~24h Apple queue

The final action. Apple reviews your build to ensure it's not malicious or broken before letting external testers install. First submission is the only one that's slow; subsequent builds for the same group are usually auto-approved within hours.

13.1Pre-flight checklist

Apple silently hides the "Submit for Review" button until ALL of these are done. Verify each:

  • ☑ App Privacy Published (not just saved) — Section 08
  • ☑ App Information complete with Age Rating + Categories — Section 09
  • ☑ TestFlight Test Information saved — Section 10
  • ☑ Privacy Policy URL loads (test in incognito) — Section 07
  • ☑ External Testing group created with the build attached — Section 12

13.2Trigger the Submit modal

The button location has changed across ASC UI revisions. As of 2026:

  1. Navigate to the build inside the external group
    TestFlight tab→ left sidebar EXTERNAL TESTING→ Your External Group→ Builds tab→ click the "Ready to Submit" yellow status text
  2. Or trigger via the build detail page
    Alternative: click the build version link (e.g. 1.0.0 (1)) → on the build's Test Information page, the submit modal may auto-trigger if pre-flight is complete.
  3. Or via adding a new external tester
    The modal sometimes pops when you try to add a tester to an external group that has an unreviewed build. This is a known UX quirk — works the same as the other paths.

13.3Complete the Submit modal

  1. Export Compliance screen
    "Does your app use encryption?" → "No, my app does not use encryption beyond standard HTTPS". This is true for most apps that just use TLS for API calls.
  2. What to Test screen
    Auto-populates from the build's "What to Test" field. Confirm:
    • ☑ Automatically notify testers
    • Text is clear and lists features the reviewer should test
  3. Click Submit for Review
    Modal closes. Build status flips from "Ready to Submit" → "Waiting for Review". A "Remove from Review" button appears on the build page (confirming submission).

13.4Apple's review timeline

First Beta App Review~24 hours
Subsequent builds for same external group2-12 hours (often auto-approved)
If you change app metadata significantly~24 hours re-review

Apple emails the contact address (from TestFlight Test Information → Contact Information → Email) with the result.

⌁ Approved Build status → "Ready to Test". The public link testflight.apple.com/join/XXXX becomes live. Anyone with an iPhone can tap → install TestFlight if needed → install your app.
⚠ Rejected Common reasons:
  • Privacy Policy URL 404s or loads parked page
  • App crashes during reviewer's testing
  • Sign-in instructions don't work or are missing
  • Apple suspects the app violates a guideline (e.g. UGC without moderation)
Fix and resubmit; round 2 is usually fast.
14

Tester Install Flow

~3 min per tester

What testers see and do on their iPhone. Useful to send as instructions to less technical testers.

14.1Via email invite (Internal or External by-email)

  1. Tester receives email
    Subject is typically "<Team Agent name> has invited you to test <App Name>". The "From" name is the Team Agent's, not whoever sent the invite — this is set at the developer account level.
  2. Tester opens the email on their iPhone
    Critical: must be on iPhone, not Android, not Mac. Tapping the link on Android shows "Invitation has been revoked or is invalid" — a misleading error message.
  3. Tap "View in TestFlight"
    If TestFlight is not installed: iPhone opens App Store → tester installs TestFlight (free Apple app) → returns to email and taps the link again.
  4. Accept the invite + install
    In TestFlight: Accept → Install. App appears on home screen with a small orange dot indicating beta.

14.2Via public link (External Testing)

  1. Tester taps the public link on iPhone
    URL format: https://testflight.apple.com/join/aBcD1234. Works for anyone on any iPhone, no email exchange needed.
  2. Same install flow as 14.1 from step 3
    Installs TestFlight if not present → opens beta page → Accept → Install.

14.3Sending feedback / crash reports

  • Crash data: automatically reported to TestFlight → Feedback → Crashes. No action needed by tester.
  • Screenshot + comment feedback: tester shakes the iPhone while in the app → "Send Beta Feedback" prompt → can include a screenshot. Visible in TestFlight → Feedback → Screenshots.
15

Troubleshooting Reference

Pattern library

Every gotcha we hit in production. Read this before you debug an issue — chances are it's listed.

15.1EAS build fails with "Sandbox: bash deny" errors

Cause: Xcode 15+ defaults ENABLE_USER_SCRIPT_SANDBOXING=YES, which prevents RN's build scripts from writing temp files.

Fix: Use the Expo config plugin in Section 01.3.

15.2CocoaPods crashes with Unicode normalization error

Cause: CocoaPods 1.16.2 + Ruby 4.0 incompatibility on macOS.

Fix:

export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8

Add to ~/.zshrc for permanent fix.

15.3Xcode picks "My Mac (Designed for iPad)" destination

Cause: Default Xcode destination on first open.

Fix: manually pick an iPhone simulator from the destination dropdown before any ⌘B or ⌘R.

15.4"This invitation has been revoked or is invalid" on TestFlight

Cause #1: Tester opened the link on a non-iOS device (Android, Mac, web).

Cause #2: Tester's iPhone is signed into a different Apple ID than the one invited.

Fix: Verify Apple ID match (iPhone Settings → top profile). If wrong, either (a) re-invite using their actual iPhone Apple ID, or (b) tester signs out and signs in with the invited Apple ID (disruptive).

15.5Public TestFlight link shows "Beta isn't accepting new testers"

Cause #1: Apple hasn't completed Beta App Review yet (still ~24h queue).

Cause #2: Tester limit hit (default 500, max 10,000).

Fix: Check the build status in ASC. If "Waiting for Review" or "In Review", just wait. If "Ready to Test", raise the tester limit in Settings.

15.6"Submit for Review" button is missing

Cause: Apple silently hides it until ALL of these are complete:

  • App Privacy Published (not just saved)
  • App Information complete (Age Rating, Categories, Content Rights)
  • TestFlight Test Information has Privacy Policy URL filled
  • Build is attached to an External Testing group

Fix: Go through Sections 08, 09, 10, 12 and verify each. Refresh the ASC page.

15.7EAS build log shows 3,400+ warnings

Cause: Third-party pod nullability warnings (Reanimated, Worklets, SDWebImage, RNSVG).

Fix: Ignore them. They're not errors. Filter actual errors:

gunzip -c <log>.xcactivitylog | strings | grep -E 'error:' | head -20

15.8iOS Simulator console spam (ignore forever)

These messages appear in every RN app on every iOS simulator:

  • patternForKey
  • ImageIO createImageAtIndex
  • TextInputUI accumulator timeout
  • CoreFoundation AddInstanceForFactory
  • BrowserEngineKit Failed to terminate
  • libapp_launch_measurement
  • ExtensionFoundation

These are Apple framework noise, not your app's bugs.

15.9Pre-auth 401 spam in cold-start logs

Cause: API hooks fire on mount before auth token is wired.

Fix pattern: gate API calls on authUser?.id:

useEffect(() => {
  if (!authUser?.id) return;
  apiService.post('/users/me/some-endpoint', payload);
}, [authUser?.id]);

15.10Splash screen frozen at boot

Cause: onLayout callback guarded on fontsLoaded fires once before fonts load, returns early, and doesn't re-fire.

Fix: Add a redundant useEffect on [fontsLoaded] that also calls SplashScreen.hideAsync().

15.11OAuth fails with "Native app ID has not been set as an allowed app identifier"

Cause: SDK (e.g. Privy, Auth0, Firebase) requires the bundle ID to be added in its dashboard allowlist.

Fix: Add com.example.yourapp to the SDK's allowed app identifiers list in its admin dashboard. No code change, no rebuild needed.

15.12"Missing Compliance" yellow badge on the build in TestFlight

Cause: ITSAppUsesNonExemptEncryption key missing from Info.plist.

Fix: Add to app.json → ios.infoPlist:

"infoPlist": {
  "ITSAppUsesNonExemptEncryption": false
}

Or click the badge in ASC → answer "None of the algorithms" → it clears for that build only.

15.13Privy / SDK "Embedded wallet proxy not initialized" red box

Cause: Transient on cold start before SDK fully initializes.

Fix: Log via console.warn instead of console.error to avoid RedBox overlay in dev. Won't fix the root cause but prevents the alarming dev UI.

15.14Build dies with "no such module 'ExpoModulesCore'"

Cause: pod install wasn't run after expo prebuild.

Fix:

cd apps/mobile/ios && pod install
16

Pushing the Next Build

~30 min total

For v1.0.1, v1.0.2, etc. — the steady-state release workflow once Section 00-13 is done once. Most one-time setup is reused.

16.1Bump version

Edit app.json:

{
  "expo": {
    "version": "1.0.1",      // user-facing semver
    "ios": { "buildNumber": "2" }   // increment for every build
  }
}

Or rely on eas.json's autoIncrement: true to handle buildNumber automatically.

16.2Build + submit in one terminal session

cd apps/mobile
eas build --profile production --platform ios   # ~25-35 min
eas submit --platform ios --latest               # ~5 min CLI + 10 min Apple processing

Or chain with &&:

eas build --profile production --platform ios && eas submit --platform ios --latest

16.3What Apple auto-approves for subsequent builds

Once your external testing group has at least one approved build, Apple usually auto-approves minor version bumps within 2-12 hours. The full ~24h review only kicks in if:

  • Major version change (1.x → 2.x)
  • New permissions added (e.g. NSCameraUsageDescription)
  • New SDKs added (e.g. payments, ads)
  • Significant UI/UX change

16.4What you DON'T need to repeat

  • APNs key upload — done once per account
  • App Privacy declaration — declared once, edited only if data collection changes
  • App Information — set once, edits trigger limited re-review
  • TestFlight Test Information — persists across builds
  • Internal Testing group + testers — persist across builds
  • External Testing group + public link — persist; new builds auto-attach (if auto-distribute is on)
  • Distribution Certificate & Provisioning Profile — EAS reuses (1 year validity)

16.5Steady-state release rhythm

git pull
# ...code changes...
git commit -am "fix: thing"
git push
cd apps/mobile && eas build --profile production --platform ios
# wait ~30 min, get email
eas submit --platform ios --latest
# Apple processes ~10 min, build appears in TestFlight
# auto-attaches to your groups (if auto-distribute enabled)
# testers get push notification of new build

Total active time per release: ~10 min terminal work + ~45 min wall-clock wait.
